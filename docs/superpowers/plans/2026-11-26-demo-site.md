# Demo Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local demo app for trying the editor as an author would, by hand or through browser automation.

**Architecture:** A new Blazor Server project, `samples/RichContent.Demo`, with one interactive page that hosts `ContentDocumentEditor` as any host would. It has its own sample documents, media picker and extension block, plus one small external script for the "Add too much text" button.

**Tech Stack:** .NET 10, Blazor Server (interactive server render mode), `SyntaxCircus.Blazor.RichContent` by project reference.

**Spec:** `docs/superpowers/specs/2026-11-26-demo-site-design.md`

## Global Constraints

- Starts with `dotnet run --project samples/RichContent.Demo` at `http://localhost:5199`; the launch profile sets `ASPNETCORE_ENVIRONMENT=Development`.
- Uses the library's public API only. Hub options stay at their defaults.
- `IsPackable` is `false`; the project is in the solution and builds with warnings as errors.
- No changes to `src/`, `tests/` or `samples/RichContent.Sample`. A library problem found with the demo is reported, not fixed here.
- No automated tests of its own. Each task is verified by building and by using the page in a real browser.
- Every control has a visible label and a stable `id`.
- No inline script: the demo's script is a file in `wwwroot`.
- Public repository: sample content is made up and names no private application.
- `.cs` files keep the repository's convention (CRLF, UTF-8 with BOM). No attribution lines in commits. Never push.

## Review Focus

1. **Reset or a new sample while the editor shows unsaved text** — expected: a fresh editor with none of the old text or errors. Task 1 recreates the editor on every load; Task 2 checks it with unsaved text.
2. **"Add too much text" with nowhere to type** (nothing focused yet, Blocks view, or editor disabled) — expected: a message saying what to do, and nothing changes. Task 2.
3. **Save while there are errors** — expected: nothing is saved, the page says why, and any earlier saved JSON is not presented as current. Task 1.
4. **Dark theme** — expected: editor text, toolbar, cards and errors are all readable. Task 1.
5. **A plain `dotnet run` from the repository root** — expected: styles and scripts load and the editor is interactive, with no console errors. Task 1.

- [ ] **Step 4: The page**

`@page "/"`. Root `<main id="demo" data-interactive="true|false">`; it turns `true` after the first interactive render. The first sample loads at start, in Write view.

| id | Control or output |
| --- | --- |
| `demo-sample` | `select` of samples; choosing one loads it |
| `demo-reset` | button: loads the selected sample again |
| `demo-disabled` | checkbox: the editor's `Disabled` |
| `demo-low-limits` | checkbox: passes `RichContentLimits.Default with { Blocks = 3, TextBytes = 500, UrlCharacters = 40 }`, otherwise `null` |
| `demo-dark` | checkbox: dark page theme |
| `demo-mode` | the view the editor reports: `Write` or `Blocks` |
| `demo-errors` | list of current errors: code, block id and message; says "No errors" when empty |
| `demo-save` | button |
| `demo-save-result` | with errors: `Not saved: N error(s).`; otherwise `Saved (save N).` |
| `demo-saved` | `pre` with the JSON of the last successful save |
| `demo-preview` | `ContentDocumentView`; with errors, a note explains why it may show nothing |

Every load (sample change or reset) must recreate the editor with `@key` on a load counter, so nothing the old one showed or failed to save survives. Replacing `Document` alone can keep on-screen text when the new document equals the old one. A load also clears errors, the save result and the saved JSON. The chosen view and settings stay.

Save follows the README's advice to hosts: refuse while `ErrorsChanged` reports anything. On refusal, clear `demo-saved`.

`demo.css`: editor beside preview on wide screens, stacked on narrow ones. Dark theme is a class on the root that sets `color-scheme: dark`, page background and text colour, and `--rt-surface` to the same background so the sticky toolbar is opaque. The theme covers the whole window.

### Task 2: "Add too much text"

**Files:**
- Create: `samples/RichContent.Demo/wwwroot/demo.js`
- Modify: `samples/RichContent.Demo/Components/App.razor`, `Components/Pages/Home.razor`, `README.md`

**Interfaces:**
- Consumes: Task 1's page and ids. The library's writing areas as they appear in the page: `[data-rt-surface]` (prose and table cells; editable when `contenteditable="true"`) and `textarea[data-rt-code]` (code cards; editable when not `readonly`), inside `[data-rt-editor]`.
- Produces: `demo-too-much` (button, with a visible hint that it needs a writing area in Write view) and `demo-too-much-result` (an empty element that only the script writes to).

- [ ] **Step 1: Add the button and result element to the page**

The button has no Blazor handler.

- [ ] **Step 2: Write `demo.js`**

Loaded by `App.razor`. All listeners are delegated on `document`, because Blazor renders and replaces the elements.

- On `focusin`, remember the target when it matches `[data-rt-surface], textarea[data-rt-code]`.
- On `mousedown` on `#demo-too-much`, call `preventDefault()`, so the caret stays where the author left it.
- On `click`: if the remembered area is missing, disconnected, not editable, or inside an `[inert]` ancestor, write `Click in a writing area in Write view first.` and stop.
- Otherwise focus the area if it is not focused, then insert `'word '.repeat(440_000)` (2.2 million characters) with `document.execCommand('insertText', false, text)`, as typing would.
- Write `Added 2,200,000 characters. The editor should now report unsaved text.` or, if `execCommand` returned `false`, `The browser did not accept the text.`

Fallback, only if the insert takes more than 15 seconds or the editor does not report it: set the textarea's `value`, or append a text node at the caret in a surface, then dispatch a bubbling `InputEvent('input')`. This is how the browser tests do it. Say in the task report which way shipped and why.

- [ ] **Step 3: README**

One sentence on what the button does.

- [ ] **Step 4: Verify in a browser**

Run the demo and check:
- in a prose area, a table cell and a code card, one at a time with a reset between: the button makes `demo-errors` show `surface-unconvertible` within 60 seconds, and Save is refused;
- with the error showing, inserting a call to action above an affected table or code card is refused and the text stays;
- Reset then gives a fresh editor: no errors, none of the added text;
- before any area has been focused, in Blocks view, and with the editor disabled: the button shows its message and nothing changes;
- no console errors beyond any the library logs for the rejected edit; record those verbatim.

Run: `dotnet build SyntaxCircus.Blazor.RichContent.slnx -c Release` — expected 0 warnings.
